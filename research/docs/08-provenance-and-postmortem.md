### 2.2 What actually happened, in one paragraph

The first real run (`eb524f3c`) ground through 7.5 hours — much of it under extended rate-limiting — and settled 64 of 65 steps, leaving only the feasibility-writer step (authoring `docs/02`) in flight when the workflow driver itself crashed with an internal JavaScript error (`Cannot read properties of undefined (reading 'slice')`). Because the settled steps' artifacts were already on disk, nothing settled was lost. The first recovery attempt — amending the crashed run, which imports its journal — reproduced the identical crash **one second after launch**: the journal contained the in-flight step, and importing such a journal deterministically kills the driver. That made re-amending pointless (the failure is structural, not transient). The working recovery was to abandon journal import altogether: a fresh, minimal workflow (`b9661b38`) that re-used the 64 settled steps' on-disk outputs and only re-ran the missing tail. The escalation run (`fa6ee73c`) then extended the program.

### 2.3 General lesson for future runs

1. **A journal containing an in-flight step is poison, not state.** Amending a crashed run imports its journal; if any step was mid-flight when the driver died, the import deterministically crashes the successor (here: identical crash, 1 s after start). An immediate second identical crash is the signature of a structural import-time failure — **stop amending after one reproduced crash; do not spend a third attempt on the same import.**
2. **Recover from artifacts, not journals, when a run dies mid-step.** The 64 settled steps had already written their outputs to disk; the journal was only needed to resume the one step that died. The fresh-minimal-workflow path (skip journal import, consume on-disk artifacts, re-run only the missing tail) recovered the whole program for the cost of one step — it is the default recovery move for driver-crashed runs.
3. **Write steps should be cheap and last.** The only unrecoverable loss in 7.5 hours was the in-flight *writer* step, because everything upstream of it had settled to disk. Long research workflows under rate-limit pressure should keep heavy evidence-gathering steps ahead and idempotent, and treat final document assembly as a thin re-runnable pass over on-disk evidence — exactly what the recovery run and this escalation run both do.
4. **Superseded-at-launch is free; know which failure modes are not.** `dwfrun-7cc7b730` cost nothing. The expensive modes are (a) driver-internal crashes on poisoned journals (fatal to the amend path, harmless to artifacts) and (b) in-flight step loss (bounded by checkpointing). Distinguishing them on the first crash saves the retry cycle.
